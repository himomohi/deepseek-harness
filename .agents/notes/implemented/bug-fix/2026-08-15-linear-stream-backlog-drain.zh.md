# Agent Note: 流式积压的线性排空

Status: implemented

[English](2026-08-15-linear-stream-backlog-drain.md) | 中文

## Problem

一个模型分片会扇出为一个持久 Session 事件、一个 API Proxy 帧、一个浏览器 WebSocket 消息；对于 SDK 消费方，还会成为一个 JSON-RPC 通知。Host `FrameQueue`、浏览器 `WebApiClient` inbox 与 TypeScript SDK 订阅曾对每次读取使用 `Array.shift()`。当休眠标签页、慢速 socket 或暂时闲置的 SDK 消费方积累大量突发项时，观测到的 V8 路径会跨过大小阈值，使积压排空急剧变为非线性，而入队仍然很快。

在 macOS 与 Node 26.7.0 上，50,000 项合成积压把本地队列成本与提供方、网络延迟隔离开来。Host mux 在 1,064.57 毫秒的 Session 追加后，排空耗时 1,077.72 毫秒；浏览器 inbox 在 110.18 毫秒的解析与入队后，排空耗时 1,510.54 毫秒；SDK 未读通知队列在 4.74 毫秒的入队后，排空耗时 200.08 毫秒；向 50,000 个已经待处理的 `next()` 调用分发则耗时 1,403.13 毫秒。原始 Session 追加路径处理每 100,000 个分片只需约 0.4 秒，JSON-RPC 解析器的实测处理能力约为每秒 782,000 帧，因此两者都无法解释随积压大小出现的陡增。

既有的[推理分片浏览器压力车道](../testing/2026-08-03-opt-in-reasoning-chunk-browser-stress.md)已按动画帧合并 UI 发布。它能保护 React 渲染，但不能消除会话归并前的队列工作，而且有意保留每个原始分片。

## Decision

Host mux／host 队列、浏览器 WebSocket inbox 与 TypeScript SDK 通知队列通过单调前进的游标读取。完全排空时清空存储；读取至少 1,024 项且已消费项占数组至少一半时定期压缩。因此，每一项的出队工作摊销为常数时间，而部分排空的长寿命积压也会释放已消费引用。

这是传输优化，不是分片合并。生产方仍立即发布第一帧，每个原始帧仍经过相同的解析与事件归并路径，FIFO 顺序与精确项数不变。第一分片前没有定时器或批次等待。

Host 与浏览器生成器会在投递每个已缓冲项前检查中止。中止会丢弃尚未投递的帧、清空数组并移除监听器，而不会花时间回放已失去消费方的 connection generation。socket 自然关闭时，其结束标记仍排在浏览器已接受的帧之后。

SDK 对已投递但未读的通知和待处理的 `next()` 调用方应用相同的游标规则。手动关闭订阅仍会丢弃未读通知并拒绝待处理调用方；运行时终止后，失败前已经投递的通知仍可排空。

## Alternatives considered

**合并或批处理模型分片。** 拒绝，因为原始模型可见输出必须能从 Session 日志重建，定时器或大小阈值还会增加第一分片延迟。分片合并只应存在于既有的动画帧 UI 发布点。

**向同步 Session 观察方施加生产方背压。** 拒绝，因为 Host WebSocket pump 已等待每次 socket 发送，而 Session 事件发布是同步的。让该观察方等待网络容量会阻塞 agent loop；通过丢帧限制积压则会违反精确 transcript 投递。队列内存仍与尚未投递的帧成正比。

**只优化 React 渲染。** 拒绝，因为实测延迟陡增出现在 React 之前：Host 队列、浏览器载体 inbox 和 SDK 订阅。既有 UI 压力决策仍然必要，但对休眠或突发消费方而言并不充分。

## Verification

确定性测试会入队并排空 20,000 个 Host mux 帧、浏览器 WebSocket 帧、SDK 未读通知和 SDK 待处理 `next()` 调用，同时断言精确顺序。独立的中止测试证明，Host 或浏览器积压会直接终止，不再产生下一条陈旧帧。既有的订阅关闭、运行时终止后排空、过滤器隔离、WebSocket 解析和重连测试也在相同的聚焦路径上运行。

使用相同的 50,000 项探针后，Host mux 排空降至 10.68 毫秒，浏览器 inbox 排空降至 9.14 毫秒，SDK 未读通知排空降至 1.31 毫秒，SDK 待处理调用方分发降至 13.54 毫秒。前后校验和一致。这些是本地合成测量，并非提供方第一 token、Internet 或实体设备证据。

生产浏览器压力车道以每 16 毫秒 128 个的突发方式发出 100,000 个推理分片。100,000 个分片全部到达；测得主线程最大延迟为 57.10 毫秒，交互延迟为 1.20 毫秒，并完成了 251 个心跳样本。

## Consequences

标签页从休眠恢复、socket 从暂时的缓慢中恢复，或 SDK 消费方完成其他工作后追赶时，不再需要先花数秒重排数组，才能呈现当前模型输出。正常的低积压流式传输仍保持逐帧行为，不增加第一帧批处理延迟。

该变更不会降低 Session 追加、逐帧 JSON 序列化与校验、网络传输、提供方首 token 时间，或 `dsh-subagent-dsh-sdk` 新运行时启动的成本。队列内存仍会随活体慢消费方尚未接受的帧数量与大小增长。处理这些成本需要独立证据；若要限制内存，还需要明确的投递或生产方背压决策。
