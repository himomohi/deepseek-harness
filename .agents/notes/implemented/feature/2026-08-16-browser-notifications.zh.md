# Agent Note: 等待回答与回复完成的浏览器通知

Status: implemented

[English](2026-08-16-browser-notifications.md) | 中文

## Problem

Web 界面会在页面内显示等待与完成状态，但用户在其他窗口工作时，无法知道智能体何时提出问题或完成回复。通知权限由浏览器控制，并要求用户手势；与此同时，会话状态可能在启动、重连或普通后台更新期间到达。若把每个观察到的等待或空闲行都视为新事件，刷新后就会重放陈旧通知。

## Decision

`@deepseek-ai/dsh-client-ui-browser-notifications` 是一个双面插件。Host 侧要求 settings 服务，并在浏览器客户端连接前同步注册持久设置 `ui-browser-notifications.enabled`，默认值为 `false`。浏览器侧向通用设置贡献一个可选择启用的行，只在该行的直接启用手势中请求通知权限，并观察 `ctx.sessions.list`。

第一份就绪的会话列表快照只作为安静基线。基线之后，进入 `pendingInteraction: question` 时发送提问通知，从 `running: true` 变为 `running: false` 时发送完成通知。如果两个事实在同一快照中同时变化，提问转换优先。基线之后发现的新会话如果已经等待回答，可以发送通知；新发现的空闲会话不会产生完成通知。

当文档可见且具有焦点时，通知会被抑制。点击通知会聚焦浏览器窗口，在来源会话仍存在时打开它，并关闭通知。浏览器权限与操作系统显示策略始终具有最终决定权。权限被拒绝后，设置界面会显示该状态，后台同步绝不会再次请求。

Web bundle 默认包含该插件。API proxy 的显式 Web settings allowlist 会向回环配置客户端暴露该 namespace；仅完成注册并不会跨越这一安全边界。韩语语言包拥有对应的韩语设置与通知词典。

## Verification

Controller 规格固定了安静基线、提问与完成转换、活动页面与禁用状态抑制、来源会话已删除时的点击、直接权限请求、权限拒绝、设置不可用以及写入失败。组件、Host schema、浏览器适配器、客户端组装、invariant 与韩语词典规格覆盖其余包侧。

`settings-chrome` 真实 Web 组合场景会在已提交的通用设置无障碍 golden 中渲染新行。由于 headless Chromium 会把通知权限固定为 denied，该场景安装一个确定性的已授权 Notifications API，再驱动启用开关，并验证 Host 设置文档记录接受后的值。浏览器适配器与 Controller 规格另行覆盖原生权限请求调用。此功能不改变模型输入或 transcript 输出，因此 ACP、headless 与 CLI transcript fixture 均无需变化。

## Alternatives considered

**使用页面内 toast。** 页面被隐藏时，toast 同样不可见，而这正是本功能要处理的状态。

**在插件激活时请求权限。** 没有用户手势时，浏览器可能拒绝权限提示，而且主动弹出的提示缺少产品上下文。通用设置中的启用项是唯一的权限请求入口。

**根据持久 `completed` 行发送通知。** 该字段是未读提醒，其值可能跨刷新与选择变化继续存在，会重放旧的完成状态，而不是表示当前运行 turn 被观察到结束。

**由 Host 发送通知。** 浏览器权限、焦点、本地化与点击导航都是浏览器拥有的事实。把投递保留在客户端插件中，可避免新增推送协议，并继续使用现有会话摘要作为事件来源。

## Consequences

用户可以选择启用后台提问与完成信号，而不会改变模型可见状态或会话日志。刷新与重连不会重放初始列表，通知点击则通过 sessions 服务保持导航。

“完成”只表示观察到的运行中 turn 已停止。通知不区分成功的智能体回复与终止错误。即使插件已发出通知，浏览器与操作系统策略仍可能抑制显示或窗口聚焦。
